# Contributing

Contributions are welcome. If you find a bug or have an idea, open an issue or send a pull request.

Write clean code that follows the style and the layout of the existing code, and make sure that all tests pass.

Send **one pull request that does one thing**. It is easier to review and faster to merge.

Before you write code, read [AGENTS.md](AGENTS.md) (the rules, commands and conventions) and
[docs/architecture.md](docs/architecture.md) for the part that you change.

## Scope

nsvim is for opening code, reading it, finding your way around it and making quick edits. It is not an IDE. Small
binaries, fast start-up and fast keys are part of its design. Each feature costs all of them for every user.

These changes need no issue first:

- **Bug fixes**, on any platform.
- **Performance**: faster keys, scrolling and start-up, and less memory.
- **Refinements of existing behavior**: Vim motions that act as in Vim, better focus and accessibility, details
  that make a platform feel right.
- **Languages**: syntax colours or text objects for a language, when the grammar is maintained and the cost in
  binary size is small. Give the size change in the pull request.
- **Bringing an existing feature to every platform** where it is missing.

A new feature needs an issue first, and a maintainer must agree before you write it. It is accepted when it fits
the scope above, works on Linux, macOS and Windows, and its cost (dependencies, binary size, start-up time) is
measured and small. A pull request that adds a feature without that agreement may be closed without a review.

## The look and the text

- Follow [docs/DESIGN.md](docs/DESIGN.md) and the [NSH Design Guides](https://nsh.dev/docs/design-guides.md).
- Colours come only from theme tokens. Corners use `rounded-(--radius)`.
- Interface text is in sentence case. Docs, comments and messages use
  [ASD-STE100](https://www.asd-ste100.org/) Simplified Technical English: short sentences, active voice, no em
  dashes or semicolons in prose.

## AI-assisted contributions

We welcome contributions written with AI, including pull requests where all of the code was generated by AI.

What matters is that the change is thoughtful, focused and well tested. The contributor is always responsible for
the final result.

Before you open a pull request, make sure that:

- The problem is real and the change is necessary, and a new feature is within the [scope](#scope).
- The code follows the existing patterns and the rules in [AGENTS.md](AGENTS.md).
- You have reviewed and tested the code: tests at the layer that owns the behavior, and a run of the app for a
  visible change (screenshots are welcome).
- The pull request does one thing, and the diff is as small as practical. Do not add unrelated refactors, cleanup
  or formatting.
- A window run uses a scratch `HOME`. The first-launch setup writes `~/.bashrc` and git's global config.

## Commits and pull requests

Commit subjects and pull request titles name the area first, then say what changed as an imperative sentence:

```
<area>: <What the change does>
```

- The area is the part of nsvim that the change is about, in lower case: `core`, `vim`, `classic`, `syntax`,
  `lsp`, `git`, `agent`, `ui`, `tree`, `finder`, `settings`, `setup`, `ipc`, `install`, `release`, `web`,
  `website`, `docs` or `ci`, or a platform (`linux`, `macos`, `windows`). Name one area only. When a change spans
  several, name the part that it is mostly about.
- The sentence starts with a capital letter, uses the imperative mood, has no final period and fits in about 72
  characters with its area. It says what the change does for a user, not which files moved.
- Do not use conventional prefixes (`fix:`, `feat:`, `chore:`). Pull requests are squash merged, and GitHub adds
  their number: `vim: Keep the column on j and k across short lines (#12)`.
- The body (optional for small changes) says why: the problem, the approach and what it costs. A change to a hot
  path gives its before and after numbers.

Examples:

```
vim: Keep the column on j and k across short lines
syntax: Add TOML, YAML, HTML and CSS colours
settings: Write each change to config.toml at once
install: Check SHA256SUMS before the archive is unpacked
```

## Development and testing

[docs/development.md](docs/development.md) gives the system packages, the commands and the code layout. Run these
before you open a pull request:

```sh
cargo fmt
cargo clippy --all-targets -- -D warnings
cargo test
nsh check
nsh build
```
